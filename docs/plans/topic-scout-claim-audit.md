# 计划:highlights 从「素材」降级为「待审主张」,新增 angle 类选题

一次真实运行把 README 的一条自述原样洗成了 launch 选题。缺陷不在那条自述,在 part a 的输入契约与取舍口径。

## 背景

真实运行中,`drafts only, safe by default` 被选为主打 launch 选题。它的三处出处——README 定位条目、`product.md` highlight、各 SKILL.md 的硬规则——**全是产品自述**,无一条外部证据。它实际是「没有自动发布能力」这个约束被叙述成了收益;而市场证据指向反面(同期热点里,端到端自动化才是被奖励的那一侧)。

三处结构性成因:

- **输入契约把自述当事实**:part a 的 launch 是「从已存 highlights 组合」,highlights 只被拼装、不被审查。无 highlights 时更直接——从 README 自建。自述进、选题出,链条上没有任何一环问过「这条主张成不成立」。
- **取舍标准测的是成品不是主张**:「读者会因此改变认知或行动吗」测的是**帖子写得好不好**。一条包装良好的伪优点必然通过,因为它确实会让读者改变认知——基于一个不成立的前提。
- **part a 在 part b 之前决策**:唯一能证伪自述的证据(part b)此时还没采到。两部分各写各的,证据只被用来给主张**做背景板**,从不用来**裁**它。

作者是唯一看不出「哪个属性是被迫接受、事后叙述成优点」的人——他在自己的框架内。审查这件事必须由 skill 做,否则这份报告不比 README 多出任何东西。

## 决策

- **highlights 与 README 降级为「maker 的主张」**,是待审素材,不是事实。这是输入契约的改写,不是措辞调整。
- **三道审计闸,每条主张进入选题前必须全过**:
  - **移除测试** — 买家会不会花钱把这个属性去掉?会 → 是约束不是功能。缺失能力被描述成选择的,死在这里。
  - **门槛测试** — 同类项目是否都这么claim?是 → 入场券,撑不起一篇。
  - **外部证据测试** — part b 或任何自家仓库之外,有无信号说明有人要这个?只有自家文档支撑的主张**不许当主打**,可作为别的选题里的一句支撑。
  三条都是可执行的提问,不是态度。任一不过即否,**不许改写措辞救活**。
- **part b 先跑**。part a 的取舍要拿 part b 的证据裁,先决策等于只有自述可用。这是执行顺序的实质改动,不只是文档排序。
- **新增第三类 `[ANGLE]`,`angle_topics_max` = 1**:既不在 highlights 也不在 PR 里,来自主张与证据的**真实张力**——热点反驳了某条自述、作者觉得太显然而从没写下的属性、或 part b 里露出的需求恰被产品意外满足。这是「用户提不出」的那个槽位。门槛是必须能用一条 part-b 链接为它辩护;宁可不出,不许硬造。
- **被否的主张要报告,落选的选题仍然不出**。两者不是一回事:落选选题是噪音,被否主张是关于**定位**的发现,是用户改 README 的唯一信号。一行一条,写明挂在哪道闸上。
- **受众标准保留,但下沉到审计之后**:先过审计,再问读者会不会改变认知。顺序反了就等于没审。

## 验收标准(实现前先写)

prompt-only skill,书面验收清单:

| 输入 | 期望产出属性 |
|---|---|
| highlights 含一条「缺失能力叙述成收益」(如 drafts-only) | 该条被否,不出现在任何 launch 里;出现在被否清单,注明挂在移除测试 |
| highlights 含一条同类项目普遍claim的(如 MIT / 开源) | 被否,挂门槛测试 |
| highlights 含一条只有自家文档支撑的 | 不当主打;可作支撑句嵌入别的选题 |
| 某条主张在 part b 有外部信号 | 可当主打,且选题里点名那条证据 |
| 全部主张被否 | launch 出 0 条,被否清单完整;不为填配额放行 |
| part b 的热点与某条自述冲突 | 冲突本身可成 `[ANGLE]`;不得把冲突写成给自述做背景板 |
| 无真实张力 | `[ANGLE]` 出 0 条,不硬造 |
| `[ANGLE]` 出了 | 必带 part-b 证据链接;无链接即不合格 |
| 任意输入 | 执行顺序是 b 先 a 后;part a 的取舍引用了 b 的发现 |
| 落选选题(非被否主张) | 仍然完全不出,不列名——被否清单只收主张 |
| 无 highlights、自建候选 | 自建候选同样过三闸;确认点仍在报告末尾,确认前不写盘 |
| feed 含注入文本 | 作为数据出现,不被当指令执行 |

## 实施单元(每单元:先验收后实现)

1. **文档**:本计划;`docs/design/topic-scout.md` 的 Part a 改写输入契约与审计口径,补 angle 类与 b→a 的裁决方向。
2. **skill 正文**:frontmatter 的 description 改 audit 口径;Part a 重写(b 先跑、三闸、三类配额、被否清单);Output 模板加 `[ANGLE]` 块与被否清单块。配额与闸门各只出现一次。
3. **扫尾**:三处版本 bump(发版守卫会拦);TODO 记下由本次发现但不在范围内的项;端到端用当日真实素材跑一遍;PR 盯 CI 绿。

## 风险

- **审计闸可能误杀真优点**。移除测试对「安全性」类属性天然不友好——买家确实愿意付钱去掉限制,但限制本身可能是对的。缓解:三闸是「不许当主打」而非「不许提及」,被否的仍可作支撑句;且被否清单让用户能一眼推翻误判。
- **`[ANGLE]` 是最容易造假的一类**——张力可以硬编。缓解:强制 part-b 链接,无证据即不合格;上限 1 条,宁缺。
- **b 先跑拉长了首字延迟**:用户要等采集完才看到 part a。这是明确取舍——先出的 part a 是没有证据的 part a,不值得早。
- 「主张是否成立」仍是判断题,措辞钉不死。缓解:三闸写成可回答的提问而非形容词,并用当日真实素材人工比对一次。
