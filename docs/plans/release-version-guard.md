# 计划：发版版本守卫

## 背景

一次 `/auto-gtm:topic-scout` 真实运行暴露了缺陷：宿主注入的提示词是**缓存里的旧 SKILL.md**，与 main 上的最新行为不符。

根因不是宿主 bug，是发版纪律缺口：#38 改了 `skills/topic-scout/SKILL.md` 却**没撞版本号**，于是仓库与缓存**版本号相同、内容不同**。插件更新按版本号判断是否已最新，同号即视为最新 → 永不重拉。用户拿到的是几分钟前那份快照，且**无从察觉**。

同类漂移已发生过三次：README badge 停在 v0.2.23（落后两版）、0.2.21 那次也漏同步过（已记在 TODO）。三处版本副本无人对账，全靠人手同步。

仓库**尚无任何 CI**——CLAUDE.md 任务生命周期第 9 步「盯 CI 转绿」指向一个不存在的东西。这是漂移能反复溜过去的结构性原因。

## 目标

让「改了产品面却没升版本」和「三处版本不一致」在合入前必然失败，而不是等用户在运行时踩到。

## 非目标

不改插件安装/更新机制本身（那是宿主的事），不引入发布自动化，不动任何 skill 行为。

## 单元 1 — 版本一致性契约

版本是**一个事实、三处副本**：两个 manifest 的 `version` 与 README 的 release badge。三者必须恒等。

验收：
- 三处任一不一致 → 检查失败，报出各自的值与位置
- 缺任一副本（文件缺失 / badge 被删）→ 失败，不静默放过

## 单元 2 — 产品面变更必须升版本

「产品面」= 用户安装后拿到的东西：`skills/`、`commands/`、两个 manifest。这些相对基线分支有改动时，版本号必须与基线不同。

验收：
- 改 `skills/**` 不升版本 → 失败，指名哪些文件触发了要求
- 改 `skills/**` 且升了版本 → 通过
- 只改 `docs/`、`README.md`（badge 除外）、计划文档 → 不要求升版本，通过
- 新版本号必须**大于**基线（语义化比较），倒退或相等 → 失败
- 基线分支不可达时（本地无 origin/main）→ 跳过此项并明示跳过，不假阳性阻塞

## 单元 3 — CI 落地

新建仓库首个 workflow，PR 与 main 推送皆触发，两个 job：

- **tests** — 跑现有 `skills/gtm-shared/tests/` 全量
- **release-guard** — 跑单元 1 + 单元 2 的检查

守卫脚本自身带测试（它是防漂移的最后一道，不能自己先坏）。

验收：workflow 在本仓库 PR 上真实触发并转绿；把版本号故意改错能让它变红。

## 单元 4 — 修复当前漂移 + 登记

- 版本撞到 `0.2.25`，三处副本对齐（这是 #38 欠下的那次 bump）
- `docs/TODO.md`：badge 双写条目改记为「已由 CI 守卫兜住，动态 badge 仍待评估」；新增 topic-scout builder-pulse「in full」与合并排序措辞相互拉扯的条目

## 顺序

单元 1、2 的测试先行 → 守卫脚本 → 单元 3 workflow → 单元 4 漂移修复与登记 → 本地跑通 → PR → 盯 CI 转绿。
